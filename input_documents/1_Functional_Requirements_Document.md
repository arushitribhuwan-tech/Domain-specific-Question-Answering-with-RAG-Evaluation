# Functional Requirements Document (FRD)
## Domain-Specific Question Answering with RAG Evaluation
**Version 1.0 • TY College Project**

---

### 1. Purpose & Scope
This document specifies the functional behavior of the Domain-Specific Question Answering (RAG) system: what the system must do, module by module, so it can be built, tested, and evaluated against clear criteria.

- **In scope:** Document ingestion, retrieval, grounded answer generation with citations, RAG evaluation, and a chat-style UI, for a single chosen domain.
- **Out of scope (MVP):** Multi-domain support, user authentication, multilingual Q&A, and automatic document refresh.

---

### 2. System Overview
The system ingests trusted domain documents, indexes them in a vector database, retrieves relevant chunks for each user question, generates an answer grounded in that context using an LLM, displays the answer with source citations, and evaluates pipeline quality using RAGAS metrics.

$$\text{User Question} \rightarrow \text{Query Embedding} \rightarrow \text{Vector Similarity Search} \rightarrow \text{Top-k Chunks} \rightarrow \text{Prompt with Context} \rightarrow \text{LLM} \rightarrow \text{Grounded Answer + Citations} \rightarrow \text{Logged for Evaluation}$$

---

### 3. User Roles / Actors
- **End User (Student / Faculty / Applicant):** Asks questions in natural language and views answers with sources.
- **Project Admin (developer/team member):** Loads/updates the domain document set and runs evaluation.
- **Evaluator (project reviewer):** Reviews the evaluation report generated by the system.

---

### 4. Functional Requirements

#### 4.1 Document Ingestion & Indexing
- **FR-1.1 (Must):** Load source documents — System shall load PDFs/text/HTML files from a designated folder.
- **FR-1.2 (Must):** Extract & clean text — System shall extract raw text and strip irrelevant content (headers, footers, boilerplate).
- **FR-1.3 (Must):** Chunk documents — System shall split cleaned text into overlapping chunks (~300–500 tokens) suitable for retrieval.
- **FR-1.4 (Must):** Attach metadata — Each chunk shall store metadata: document name, section/page number, chunk ID.
- **FR-1.5 (Must):** Generate embeddings — System shall convert each chunk into a vector embedding using a chosen embedding model (`sentence-transformers/all-MiniLM-L6-v2`).
- **FR-1.6 (Must):** Persist vector index — System shall store embeddings and metadata in a local vector database (`ChromaDB`) for reuse across sessions.
- **FR-1.7 (Should):** Re-index on demand — Admin shall be able to trigger re-indexing after adding/removing documents.

#### 4.2 Query & Retrieval
- **FR-2.1 (Must):** Accept user question — System shall accept a free-text question via the UI.
- **FR-2.2 (Must):** Embed the query — System shall convert the user's question into a vector using the same embedding model as ingestion.
- **FR-2.3 (Must):** Similarity search — System shall retrieve the top-k most similar chunks from the vector database.
- **FR-2.4 (Should):** Configurable top-k — System shall allow top-k to be configured (default k=4–6).
- **FR-2.5 (Could):** Hybrid retrieval — System should optionally combine keyword search (BM25) with vector search to improve recall.
- **FR-2.6 (Could):** Re-ranking — System should optionally re-rank retrieved chunks using a cross-encoder before passing to the LLM.

#### 4.3 Answer Generation
- **FR-3.1 (Must):** Construct grounded prompt — System shall build a prompt containing the user question and only the retrieved chunks as context.
- **FR-3.2 (Must):** Generate answer via LLM — System shall send the prompt to the configured LLM and return a natural-language answer.
- **FR-3.3 (Must):** Restrict to evidence — System shall instruct the LLM to answer only from provided context and avoid outside knowledge.
- **FR-3.4 (Must):** Insufficient-evidence handling — System shall return a clear "not enough information" response when retrieved context does not answer the question.
- **FR-3.5 (Must):** Attach citations — System shall return, alongside the answer, the source document name and page/section for each chunk used.
- **FR-3.6 (Should):** Swap LLM/model config — System should allow switching the underlying LLM without code changes (config-driven).

#### 4.4 Evaluation Module
- **FR-4.1 (Must):** Load test QA set — System shall load a prepared set of question–reference-answer pairs for evaluation.
- **FR-4.2 (Must):** Run batch evaluation — System shall run the full RAG pipeline over the test set and record each answer, retrieved context, and reference.
- **FR-4.3 (Must):** Compute RAG metrics — System shall compute context precision, context recall, faithfulness, answer relevance, and answer correctness via RAGAS.
- **FR-4.4 (Must):** Measure latency — System shall record retrieval time and generation time per query.
- **FR-4.5 (Must):** Generate evaluation report — System shall output a summary report/table of metric scores across the test set.
- **FR-4.6 (Could):** Compare configurations — System should allow comparing metric scores across different chunk sizes, top-k, or LLM choices.

#### 4.5 User Interface
- **FR-5.1 (Must):** Chat interface — System shall provide a text input for questions and display answers in a chat-style layout.
- **FR-5.2 (Must):** Source display — System shall display citations (document name, page/section) beneath each answer.
- **FR-5.3 (Should):** Loading/response state — System shall show a loading indicator while retrieval/generation is in progress.
- **FR-5.4 (Should):** Evaluation dashboard view — System should display evaluation metric results in a simple table or chart within the UI.
- **FR-5.5 (Could):** Document upload panel — System could allow an admin to upload new documents through the UI instead of a folder.

---

### 5. Non-Functional Requirements
- **Performance:** End-to-end response time should be under ~10 seconds per query on a standard laptop (CPU-only, 3B–8B LLM).
- **Usability:** UI shall be usable without technical training — plain-language question box and clearly labeled sources.
- **Reliability:** System shall handle malformed/unreadable documents gracefully without crashing the ingestion pipeline.
- **Portability:** System shall run fully offline/locally on a single laptop (Windows/macOS/Linux) with no mandatory paid services.
- **Maintainability:** Configuration (chunk size, top-k, model names) shall be externalized (`config.yaml`), not hardcoded.
- **Cost:** $0 — all core components are free and open-source.

---

### 6. Use Case Scenarios
- **UC-1 (Ask a question):** User types a question $\rightarrow$ system retrieves relevant chunks $\rightarrow$ generates a grounded answer $\rightarrow$ displays answer with citations.
- **UC-2 (No relevant information):** User asks an out-of-domain question $\rightarrow$ retrieval returns low-relevance chunks $\rightarrow$ system responds that it cannot answer from available documents.
- **UC-3 (Admin refreshes documents):** Admin adds a new PDF to the source folder $\rightarrow$ triggers re-indexing $\rightarrow$ new document becomes searchable.
- **UC-4 (Run evaluation):** Evaluator triggers the evaluation script $\rightarrow$ system runs the test QA set through the pipeline $\rightarrow$ report of metric scores is generated.

---

### 7. Data Requirements
- **Domain document set:** 20–50 trusted PDFs/notices/web pages for the chosen domain.
- **Test QA set:** 30–60 manually verified question–reference-answer pairs, tied to the same documents.
- **Vector store:** Persisted embeddings + metadata (document name, page/section, chunk ID).
- **Evaluation logs:** Stored question, retrieved chunks, generated answer, reference answer, and metric scores per run.

---

### 8. Assumptions & Constraints
- Source documents are text-extractable (not scanned images) or OCR is applied beforehand.
- A single domain and a fixed document set are used for the MVP; no live multi-domain switching.
- Development and evaluation are performed on a single laptop with 8–16 GB RAM, CPU-only or entry-level GPU.
- No user authentication or multi-user session handling is required for the MVP.

---

### 9. Acceptance Criteria
1. A user can ask a domain question and receive an answer with at least one correct source citation.
2. Out-of-domain questions correctly trigger the "not enough information" response instead of a fabricated answer.
3. Running the evaluation module on the test QA set produces all five RAGAS metrics plus latency for every question.
4. The full pipeline (ingestion $\rightarrow$ retrieval $\rightarrow$ generation $\rightarrow$ evaluation) runs end-to-end on a single laptop using only free/open-source components.
